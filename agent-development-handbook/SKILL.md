# AGENT 开发手册

五条硬规则：**三件套**、**git 先问**、**TODO / CHANGELOG 分工**、**方案先行**、**版本号先问**；复杂项目再加一条——**学会指挥**（写 → 审 → 定，见 §4）。
它们服务同一个目标：下一个会话只读仓库，就知道现在做到哪、为什么这么做、下一步是什么。

> 项目自己的 `AGENTS.md` 在命令、目录、架构、代码风格上优先于本手册；但它不能用来绕开用户定的硬约束（git 写操作先问、改版本号先问、不确定先问）。
> 项目规则**只能加严，不能放松**：项目把 `fetch` 也列进「先问」清单，就照项目办；项目写「版本号可以自己升」，按本手册办，仍然要问。
> 两边打架时先分两种：**说的是同一件事**（谁先问、能不能自己升版）→ 取更严的那条，并把差异当场说给用户听；**说的不是同一件事**（项目要求每条 CHANGELOG 都确认，手册只管版本段）→ 停下来问用户。不要默默挑一条执行。

## 开工前 60 秒

1. 读 `AGENTS.md`（命令、目录、禁令），再读 `TODO.md` 顶部和 `CHANGELOG.md` 最新一段（约定与进度）。
2. `git status --short` + `git log --oneline -5`：看清有没有未提交改动、最近的提交风格。
3. 判断这次要不要出方案（§4）。要，就先出方案再动文件。

错别字、单行修复可以只做第 2、3 步；其余改动别省第 1 步。

## 1. 三件套

| 文件 | 写什么 | 不写什么 |
|---|---|---|
| `AGENTS.md` | 给 agent 的操作说明：真实命令、目录职责、架构、安全约束、测试与升级注意点、已知坑 | 进度、新闻、一次性计划 |
| `TODO.md` | **唯一**未完成清单：进行中 / 待办 / 阻塞，每条可验收 | 已完成的事、愿望清单、讨论记录 |
| `CHANGELOG.md` | 已完成且用户能感知的变化，按版本分组 | commit log 的复述、「优化代码」 |

- 三个文件都放仓库根，各只有一份；不要 `TODO-2.md`、`docs/CHANGELOG-2026.md`。
- 缺失时：`TODO.md`、`CHANGELOG.md` 可直接建骨架（见 `references/templates.md`）；`AGENTS.md` 只写**验证过**的事实（命令真跑通过、目录真存在），拿不准的约定先问用户。
- 仓库已经用 Issues / 项目板跟踪任务时，先问再接，并说清谁是唯一来源（一般 Issues 管任务，TODO 只留 agent 手头在做的和阻塞项），别造第二套完整清单。
- 「进行中 / 待办 / 阻塞」之外允许两个**可选**区：**明确不做**（写清为什么不做、什么条件下重启）和**想法（未承诺）**（无用户点名，且跨过一次发版没动就删；没有版本号的仓库按 30 天算）。它们不必非在文件末尾——放对应里程碑子节底部也行，只要混不进待办就行。少了这两区，被否掉的想法会反复溜回待办，清单越滚越长。

## 2. Git：先问，再做

**分支命名**：新建仓库默认分支一律 `master`（本机已设 `init.defaultBranch=master`）；不要建议改成 `main`，也不要自作主张改名。

**必须问**：`commit`（含 `--amend`）、`push`、`tag`、`pull`（= fetch + merge）、建 / 删 / 改名 / 切换分支（`switch`、`checkout <branch>`）、`merge`、`rebase`、`cherry-pick`、`reset`、`revert`、`restore` / `checkout` 丢弃改动、`stash drop|clear`、`clean`、`rm`、`mv`、改 remote、`gh pr|release`、加 submodule。

**不必问**：`status`、`diff`、`log`、`show`、`blame`、`rev-parse`、`ls-files` 等只读命令；`fetch` 可以跑，但要说明拉了什么，别拿 `fetch` 当 `pull`（项目 `AGENTS.md` 另有更严规定时按项目办）。

**随提交一起问**：把本次已审阅的文件 `git add` 进去，不必为每个 `git add <file>` 单独再问；`add -A` / `add .` 会扫入无关改动，仍要单独问，并在征询里列出 stage 了哪些文件。

怎么问：

- 一次问一批：贴 `git status --short` 摘要 + 逐条命令 + 拟用提交信息 + 影响（推到哪、会不会动已推送历史）。
- 等**明确同意**再执行。同意只覆盖这一次、这几条：批了 commit 不等于批了 push，批了 push 不等于批了打 tag。
- 不替用户决定：用户已有未提交改动时先问，不擅自 stash / commit；不用 `--no-verify` 跳过 hook（hook 失败就修）；不 force-push、不移动已推送 tag、不 amend 已推送提交。
- 命令失败先读报错，不要换个写法硬重试。

提交信息：`feat: / fix: / docs: / refactor: / perf: / test: / build: / ci: / style: / chore:` + 一句话说清改了什么；一次提交做一件事。项目有约定就照 `git log --oneline -10` 的风格来。

## 3. TODO 与 CHANGELOG

一条待办的完整生命周期：

```text
写进 TODO（可验收）→ 做 → 从 TODO 删除 → 有用户可感知变化就记 CHANGELOG → 征得同意后提交
```

- **完成即搬家**：同一轮里删 TODO；有用户可感知变化就同步写 CHANGELOG。两处都留 = 两处都不可信。
- 纯内部改动（重构、补测试、注释）没有用户可感知结果：直接从 TODO 删除，不进 CHANGELOG；要留痕靠 commit message。
- TODO 每条要能独立验收：写「手机端设置页在 390×844 下全屏、导航横向」，不写「优化移动端」。
- 超过一屏就分「进行中 / 待办 / 阻塞」；阻塞项标清等谁、等什么，别挂在「进行中」。「明确不做」「想法（未承诺）」不混进待办，放对应里程碑子节底部或文件末尾。
- 发现的、但这次不做的事也要落进 TODO，别只留在对话里。
- CHANGELOG 用 Keep a Changelog：`## [Unreleased]` + 六个小节（`Added / Changed / Deprecated / Removed / Fixed / Security`），写用户能感知的结果。小节名可以用中文（`新增 / 变更 / 弃用 / 移除 / 修复 / 安全`），但**全仓库统一一种写法**，同一个文件里不要中英混排；仓库接了 `conventional-changelog`、`standard-version`、`release-please` 这类按英文标题解析的工具时，标题必须用英文。

### 版本号：改之前先问

- **做完一步 ≠ 该发版。** 不要因为「这个功能做完了」就把 `0.0.2` 改成 `0.0.3`，也不要每轮任务都递一个版本号。
- 以下都算发版动作，**每次都先问用户**，上次同意过不代表这次也同意：改 `package.json` / `pyproject.toml` / `Info.plist` 等版本字段；把 CHANGELOG 的 `[Unreleased]` 切成 `## [x.y.z]`；打 tag；`npm publish`、`gh release`、商店 / TestFlight 上传。
- 打 tag 先问。移动或覆盖已推送的 tag 不做（见 §2），除非用户了解风险后明确要求。
- 版本变更本身也是一次提交，同样按 §2 先问，别夹在功能提交里。
- 问的时候给：当前版本、建议版本与理由、要改的文件、要不要同时打 tag / 发布。
- 版本号格式与升哪一段，以 [语义化版本 2.0.0（中文）](https://semver.org/lang/zh-CN/) 为准：X = 不兼容的公共 API 改动，Y = 向后兼容的新功能，Z = 向后兼容的修复；进位时低位归零（`1.2.3` → `2.0.0`）；预发布写 `1.0.0-rc.1`，`+build` 元数据不参与版本比较。
- `0.y.z` 是初始开发阶段，公开 API 随时可能变；这不等于版本号可以随便跳——升级理由要对应实际改动，且照样先问。
- 功能提交不带版本号：做完先留在 `[Unreleased]`，等用户说「发版」再单独一次提交做版本变更。这样能单独回滚，也不会出现 tag 和包内容对不上。
- 改版本时同步检查 README、安装命令、文档里引用的版本号和 tag，不要只改 `package.json`。
- 往 `[Unreleased]` 加条目随时可以，那不涉及版本号；出现具体 `## [x.y.z]` 才需要问。

## 4. 方案先行

**要方案**：新功能；跨文件改动（≥3 个文件或动公共接口 / 数据结构）；依赖、构建、发布、迁移；删除或重命名；需求有两种读法（先按 §5 问清再写方案）。

**可跳过**：错别字、单行修复、用户已给出明确步骤——但仍先用一句话说清要改什么。

短方案五段，一屏看完：

```text
目标 / 不做：
改动文件：
步骤（≤5）：
风险与回滚：
验证方式：
待你决定：
```

- 出方案 → **停** → 等同意再动代码。用户说「直接做 / 你定」才免掉这一步。
- 开放问题摆在「待你决定」，不要用「假设…」把不确定藏进实现。方案可以列「关键假设」，但每条要写明「不成立时怎么办」，并让用户确认。
- 需求本身有两种读法 → 先按 §5 问清，不要先写方案再让用户在两个错方向里选。
- 范围变大就回来说一声，别把方案悄悄做成另一个东西。

### 复杂项目：写方案 → 审方案 → 定方案（学会指挥）

复杂项目的方案不要一个人憋：让一个 AI 写，让另一个 AI 挑错，我只看代码核对、取舍、定稿。

**什么时候走这一套**：新架构 / 跨模块改造、数据或接口迁移、发布与回滚策略、技术选型、需求要反复澄清、一天内收不完。局部修 bug、改文案、加一个字段——不要为了流程好看硬套。

| 棒次 | 谁 | 给什么 | 要什么 |
|---|---|---|---|
| 1 写 | `subagent`（新上下文） | 目标、约束、相关文件路径、验收标准 | 短方案（目标 / 不做、步骤、风险、验证）+ 关键假设 + 拿不准的点 |
| 2 审 | 另一个 `subagent`（新上下文） | 方案原文 + 自己读仓库 + 「默认它有问题」 | 结论（可行 / 有风险 / 不建议）+ ≥3 条具体问题（引用文件 / 接口 / 失败场景）+ 最担心的假设 + 缺哪些验证 |
| 3 定 | 我 | 两份产出 + 亲自核对代码 | 逐条采纳 / 驳回并写理由 → 最终方案 → 分歧留给用户 |

**独立性是这套流程唯一的价值**：

- 写的人不审自己的方案；审的人不知道写的人是谁，也不知道我倾向哪个结论。同一模型也至少要换上下文；条件允许就给审阅换一个模型（`list_subagent_models` 查路由），少一点同源盲点。
- 不要把「我觉得应该用 A」写进审阅提示词——那只是在找背书。
- 审阅提示词必须禁止空泛评价（「方案很合理」「建议完善细节」），要求落到文件、函数、失败场景。
- 派活的 `description`（任务标题）带上模型名，例如 `审阅方案 · GLM-5.1`：列表里一眼看出谁在跑，结果出自哪个模型，换模型的评审也不会被认串。

**我这一棒不能省**：

- 双方引用的文件、命令、版本，我自己去仓库核对；AI 评审也会编路径。
- 采纳要写理由，驳回也要写理由；两边打架的地方不要抹平，原样列进「待你决定」。
- 子代理只出方案，不改代码、不 commit、不 push；git 同意规则对它们同样有效，最后由我向用户申请。

**成本与例外**：这套流程大约多花一倍时间，所以只给复杂项目。要比较两三种路线时，优先让两个 writer 用 `subagent` 并行各写一版再让 reviewer 对比；`workflow` 只在用户明确要求、或确实要大规模编排时用，用前先说明。

## 5. 不确定就问

| 情况 | 为什么不能猜 |
|---|---|
| 需求有两种读法 | 选错要重做，越晚越贵 |
| 两个方案都合理 | 取舍取决于用户对钱 / 时间 / 维护的偏好 |
| 会删数据、改历史、发版、动线上 | 不可逆 |
| 要账号、密钥、外部服务、付费 | 用户不出面就做不下去 |
| 命名、公共 API、目录结构 | 改起来牵连全仓库 |
| 与 `AGENTS.md` 或现有文档冲突，且不是「项目更严」那种 | 说明至少有一处是错的 |
| 测试失败但原因不明 | 掩盖失败比失败更糟 |
| 想顺手扩大范围 | 那不是这次的任务 |

怎么问：一次一个主题，最多 3 个问题；给选项 + 推荐项 + 代价，让用户点头就行，别问「你觉得呢」；自己的默认选择和理由要写出来。

不要：猜一个、做完再解释；把问题写成 TODO 挂着；用「我理解你的意思是…」代替提问。

答案若改变长期约定，提议写回 `AGENTS.md`；若 `AGENTS.md` 由用户维护，不要直接改，给出 diff 建议让用户决定。

## 6. 收尾清单

- [ ] 做完的已从 TODO 移走，新发现的已记进 TODO
- [ ] CHANGELOG 有对应用户视角条目（纯内部改动可没有）
- [ ] 验证真跑过（命令 + 结果）；没跑的在回复里说明
- [ ] git 操作都征得过同意，没有未说明的残留改动
- [ ] 没有擅自改版本号、切版本段或打 tag（要发版先问过）
- [ ] 项目规则与手册冲突的地方已说给用户，没有默默挑一条执行
- [ ] 回复说清：改了什么、没做什么、下一步 / 待决定

## 反模式

| 反模式 | 后果 |
|---|---|
| 先写代码，最后补方案 | 方案变成事后合理化，用户失去否决权 |
| 一个 commit 混三件事 | 出问题无法单独回滚 |
| TODO 完成了打勾留着 | 清单越来越长，没人再读 |
| CHANGELOG 抄 commit message | 用户视角丢失，等于没写 |
| 「顺手」push / 打 tag | 不可撤回的动作没人批准过 |
| 改一步就升版本号 | 版本失去含义，tag、包、CHANGELOG 对不上 |
| 猜需求然后解释「我以为」 | 返工，还消耗信任 |
| 把不确定挂成 TODO | 问题从「要决定」变成「没人决定」 |
| 复杂方案只写不审，或让同一上下文自审 | 盲点原样带进实现，评审变成盖章 |
| 项目规则与手册冲突时默默挑一条 | 用户不知道有两套规则，标准和回滚都失去依据 |
